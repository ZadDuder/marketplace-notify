# Marketplace Notify

Сервис прикладных уведомлений для кабинетов Ozon Seller и М.Видео. Для Ozon в Telegram отправляются только события, требующие реакции менеджера: новые FBS/realFBS-заказы, возвраты на согласовании и к получению, товары к вывозу до утилизации, жалобы со сроком спора, приёмка поставок FBO и акты на согласование. Для М.Видео отслеживаются доступные через API кабинета FBS-заказы, этапы сборки и доставки, приёмка, отмены и повторные поставки.

## Целевая production-архитектура

Сервис рассчитан на единственный self-hosted production-узел.

- `APP_MODE=full` принимает Ozon webhook и выполняет polling Ozon и М.Видео.
- Каждый кабинет Ozon использует отдельную Telegram-форум-группу. Внутри неё события разделяются по собственной карте `telegram_topics`; кабинет дополнительно указан в тексте сообщения.
- М.Видео использует отдельную Telegram-форум-группу; заказы направляются в тему `sales`, а технические ошибки остаются в логах.
- Прежняя общая группа кабинетов не входит в активные production-маршруты.
- Новости Ozon выключены по умолчанию через `NEWS_NOTIFICATIONS_ENABLED=false`.
- Production-узел запускается с host-network overlay: приложение слушает только `127.0.0.1:8080`, а наружу HTTPS публикует Caddy.
- При миграции прежний узел используется только для сверки состояния. После подтверждения нового узла webhook переключается, данные и резервная копия проверяются, затем прежний экземпляр выводится из эксплуатации.

Relay-режим больше не является частью целевой production-схемы. Он может оставаться в коде для совместимости или аварийного сценария, но новые развертывания должны использовать основной узел в `full`.

## Быстрый запуск

Подготовьте `.env` на сервере без публикации его содержимого. Минимальные значения целевой схемы:

```dotenv
APP_MODE=full
TELEGRAM_BOT_TOKEN=<токен company-бота>
TELEGRAM_DEFAULT_CHAT_ID=-100<резервный id группы>
NEWS_TELEGRAM_BOT_TOKEN=
NEWS_TELEGRAM_CHAT_ID=
NEWS_NOTIFICATIONS_ENABLED=false
```

`TELEGRAM_BOT_TOKEN`, `TELEGRAM_DEFAULT_CHAT_ID`, `WEBHOOK_SECRET`, `OZON_ACCOUNTS_JSON` и `MVIDEO_API_KEY` заполняются эксплуатационными значениями и в документацию не копируются.

Запуск:

```bash
docker compose -f docker-compose.yml -f docker-compose.relay.yml up -d --build
docker compose -f docker-compose.yml -f docker-compose.relay.yml ps
```

В этом сочетании overlay сам задаёт `BIND_HOST=127.0.0.1` приложению и `CADDY_UPSTREAM=127.0.0.1:8080` для Caddy. Порт приложения не должен быть доступен извне напрямую. Не запускайте параллельно старую relay-конфигурацию.

Проверка:

```bash
curl -fsS https://<production-host>/health
curl -fsS https://<production-host>/routes
docker compose -f docker-compose.yml -f docker-compose.relay.yml logs --tail=200 ozon-notify
```

`/health` должен показывать режим `full`. Полный список webhook-маршрутов открывайте только с заголовком `X-Ozon-Notify-Secret`; публичный ответ маскирует секреты.

## Локальный запуск

```bash
cp .env.example .env
python -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
PYTHONPATH=src python -m ozon_notify.app
```

## Telegram-маршрут

Company-бот должен быть администратором каждой форум-группы с правом управления темами. У каждого кабинета задаётся собственный `telegram_chat_id` вида `-100...` и собственная карта `telegram_topics` с Telegram `message_thread_id`:

| Ключ | Раздел |
| --- | --- |
| `sales` | Продажи и заказы |
| `rfbs` | Заказы realFBS |
| `messages` | Жалобы покупателей |
| `returns` | Возвраты |
| `supplies` | Поставки и приёмка |

Старые ключи `logistics`, `finance`, `news` и `system` поддерживаются конфигурацией для совместимости, но текущий Ozon-фильтр их не использует. Раздел для активного события обязателен: если его ID ещё не задан, сообщение не отправляется в `General` и остаётся доступным для следующей проверки. `TELEGRAM_DEFAULT_CHAT_ID` остаётся только резервным маршрутом для старых конфигураций без собственного `telegram_chat_id`.

В production `NEWS_NOTIFICATIONS_ENABLED=false`: новости не смешиваются с рабочими событиями. Возможность news-poller сохранена и включается только явным изменением флага.

Для первого запуска рекомендуется `BOOTSTRAP_SEND_EXISTING=false`: текущая история фиксируется как исходное состояние, а в Telegram уходят только новые события.

Для FBS/realFBS подробное уведомление формируется по полному ответу актуального Ozon API v4 не позднее следующего важного цикла. На одно отправление создаётся одна карточка с временем поступления, номером заказа и отправления, товарами, количеством и сроком подготовки. Рутинные статусы, отмены, изменения срока и сообщения о курьере не отправляются.

## М.Видео

Для подключения задайте `MVIDEO_API_KEY`. Ключу нужны права `Просмотр заказов` и `FBS: Просмотр заказов`. В production обязательно задайте отдельную форум-группу в `MVIDEO_TELEGRAM_CHAT_ID` и карту тем `{"sales": <id темы заказов>, "system": <id системной темы>}` в `MVIDEO_TELEGRAM_TOPICS_JSON`. Наследование маршрута первого кабинета Ozon оставлено только для обратной совместимости и не используется в целевой конфигурации.

Polling выполняется раз в `MVIDEO_POLL_SECONDS` через официальный API Личного кабинета поставщика `https://api.sellers.mvideo.ru`. Новые резервы проверяются отдельным методом, а статусы сверяются в скользящем окне `MVIDEO_LOOKBACK_HOURS` (по умолчанию 30 дней), чтобы не потерять длительный заказ. В раздел `sales` приходят новые FBS-заказы, ожидание и начало сборки, ожидание доставки, прибытие машины на склад М.Видео, результат приёмки, отмены и запросы на повторную поставку. Сообщение содержит номер резерва, код товара М.Видео, артикул поставщика, количество, номер поставки, объект и время по Москве, когда эти поля возвращает API.

Текущий API кабинета не публикует read-only списки DBS-заказов, возвратов и финансовых операций для этого ключа, поэтому сервис не заявляет такие уведомления. Если контракт М.Видео расширится, источники можно добавить отдельно без изменения Telegram-маршрута.

## Прикладные события Ozon

Возвраты rFBS проверяются по деталям заявки: уведомление создаётся только когда
Ozon возвращает доступные действия продавца. Сообщения Ozon дополнительно
распознаются как запрос решения по возврату, возврат в ПВЗ, вывоз до утилизации,
жалоба со сроком спора, приёмка или акт FBO. Обычные сообщения, вопросы,
финансовые операции, курьерские статусы и технические события не отправляются.

Для поставок сервис сверяет каждую поставку отдельно. Переход в `COMPLETED`
создаёт карточку о результате приёмки; состояние подтверждения отчётов создаёт
отдельную карточку о необходимости согласовать акт. Seller API не выполняет
решение за менеджера: принять или отклонить возврат/акт нужно в Ozon Seller.

## Webhook Ozon

Сервис сверяет список webhook в Ozon: сохраняет уже правильный URL, переносит существующую подписку на текущий `PUBLIC_BASE_URL` или создаёт новую. Если операция не удалась или API-ключу не хватает роли, polling продолжает работу, а ошибка записывается в технический лог без сообщения менеджерам.

После миграции проверяйте webhook на новом узле, затем отключайте старый экземпляр. Webhook и polling используют общий краткосрочный маркер статуса отправления, чтобы один факт не пришёл дважды. Не оставляйте оба production-узла активными надолго: этот маркер рассчитан на один экземпляр с общей SQLite.

## Добавление кабинета

Измените `OZON_ACCOUNTS_JSON` в `.env` одной строкой. Для нового кабинета задайте уникальный `slug`, Ozon credentials, ID его собственной форум-группы и как минимум темы `sales`, `rfbs`, `messages`, `returns` и `supplies`. При первом подключении `BOOTSTRAP_SEND_EXISTING=false` фиксирует текущую историю без массовой отправки старых событий. После изменения пересоздайте контейнер:

```bash
docker compose -f docker-compose.yml -f docker-compose.relay.yml up -d --build --force-recreate
```

Не помещайте в README, логи, issue или commit реальные Telegram-токены, API-ключи маркетплейсов, пароли и relay/webhook-секреты.
