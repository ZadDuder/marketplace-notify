# Эксплуатация

## Целевая топология

Production работает на единственном self-hosted узле в `APP_MODE=full`.

- Приложение на production-узле принимает Ozon webhook, хранит SQLite и выполняет polling по кабинетам Ozon и М.Видео.
- Company-бот отправляет события каждого кабинета Ozon в отдельную форум-группу. У каждой записи `OZON_ACCOUNTS_JSON` собственные `telegram_chat_id` и `telegram_topics`; кабинет также указывается в тексте уведомления. `TELEGRAM_DEFAULT_CHAT_ID` используется только как резервный.
- М.Видео использует отдельную форум-группу с явными `MVIDEO_TELEGRAM_CHAT_ID` и `MVIDEO_TELEGRAM_TOPICS_JSON`: `sales` для заказов; технические ошибки пишутся только в лог.
- Прежняя общая группа кабинетов не входит в активные production-маршруты.
- News-poller в production выключен через `NEWS_NOTIFICATIONS_ENABLED=false`.
- Docker Compose overlay `docker-compose.relay.yml` переводит `ozon-notify` и Caddy в host-network, привязывает приложение к `127.0.0.1:8080` и направляет Caddy на этот локальный upstream.

Команда production-запуска:

```bash
cd /opt/ozon-notify
docker compose -f docker-compose.yml -f docker-compose.relay.yml up -d --build
```

Прежний VPS не входит в целевую схему. До вывода из эксплуатации он используется только для сравнения состояния и проверки, что новый узел принял webhook, polling и маршрутизацию сообщений.

## Миграция и вывод российского VPS

1. На новом узле подготовить `.env` с `APP_MODE=full`, `NEWS_NOTIFICATIONS_ENABLED=false`, company-ботом в `TELEGRAM_BOT_TOKEN` и отдельной форум-группой каждого кабинета в `OZON_ACCOUNTS_JSON`. News-переменные оставить пустыми. Секреты передавать только защищенным способом.
2. Перенести SQLite и проверить владельца каталога `data` (`10001:10001`). Не переносить секреты в образ или документацию.
3. Запустить новый узел с host-network overlay и убедиться, что `/health` показывает `full`, HTTPS отвечает, Caddy проксирует на `127.0.0.1:8080`, прямой внешний доступ к `:8080` закрыт, а логи не содержат секретов.
4. Проверить маршрут без тестовой отправки: бот видит каждую группу как форум, является администратором с `can_manage_topics`, а конфигурация каждого кабинета содержит девять корректных `message_thread_id`.
5. Сверить bootstrap-маркеры и дедупликацию, чтобы после миграции не отправить исторические записи повторно. При первом запуске без истории использовать `BOOTSTRAP_SEND_EXISTING=false`.
6. Перенастроить Ozon webhook на публичный URL нового узла и проверить доставку. Сервис использует `notification/list`, затем оставляет правильный URL, обновляет существующую подписку или создаёт новую. Только после этого остановить приложение и Caddy на прежнем VPS.
7. В течение согласованного окна наблюдения проверить новый узел по `/health`, логам, polling и Telegram. После успешной проверки удалить старый VPS из мониторинга и вывести его из эксплуатации.

Если миграция не подтверждена, старый VPS не считать выведенным из эксплуатации: зафиксировать причину, исправить новый узел и повторить проверку. Не держать два узла активными без контроля дедупликации.

## Проверки после деплоя

```bash
docker compose -f docker-compose.yml -f docker-compose.relay.yml ps
docker compose -f docker-compose.yml -f docker-compose.relay.yml logs --tail=200 ozon-notify
curl -fsS https://<production-host>/health
curl -fsS https://<production-host>/routes
```

Публичный `/routes` маскирует webhook-секрет. Полный URL для ручной настройки Ozon запрашивайте только с секретным заголовком и не сохраняйте в общих логах.

## Диагностика Telegram

Проверяйте по порядку:

1. Company-бот является администратором каждой группы, у группы включены темы, а у бота есть право управления ими.
2. У каждого кабинета собственный `telegram_chat_id`, а `telegram_topics` содержит корректные ID как минимум для `sales`, `rfbs`, `messages`, `returns` и `supplies`.
3. `NEWS_NOTIFICATIONS_ENABLED=false`, поэтому новости Ozon не попадают в рабочие группы.
4. В логах нет ошибки авторизации, сетевого таймаута или ответа Telegram с ограничением частоты.
5. После изменения `.env` контейнер пересоздан:

```bash
docker compose -f docker-compose.yml -f docker-compose.relay.yml up -d --force-recreate
```

Клиент Telegram отправляет сообщения последовательно и повторяет запрос после `429` с учетом `retry_after`. После сетевых ошибок событие остается доступным для следующего polling-цикла.

Кабинет никогда не откатывается в `General`: если ID тематического раздела отсутствует, отправка откладывается до исправления `telegram_topics`. Успешные отправки фиксируются в логах с `account`, `topic` и `thread_id`, без текста сообщения и секретов.

## Заказы realFBS

Новый realFBS-заказ определяется по `integration_type_flow` или `tpl_integration_type`. Неполный `TYPE_NEW_POSTING` webhook сохраняет маршрут отправления, но не создаёт сообщение без названия товара. Подробную карточку формирует ближайший важный polling-цикл из полного ответа Ozon. При стандартном интервале задержка составляет не более минуты.

Маркеры `fbs-announced:<slug>:<posting_number>` и `rfbs-announced:<slug>:<posting_number>` гарантируют одну карточку на отправление. В ней должны быть кабинет, номер заказа и отправления, время поступления по Москве, срок подготовки, товары и количество. Обычные переходы между статусами, отмены, изменение срока и приезд курьера фиксируются или игнорируются без Telegram-сообщений.

Перед первым развёртыванием этого правила на существующей базе заполните соответствующие FBS/rFBS-маркеры для уже известных записей `posting-route:*`. Это предотвращает повторную рассылку активных заказов. Перед операцией остановите приложение и сделайте SQLite backup.

## Возвраты, утилизация и поставки

- rFBS-возврат отправляется только при непустом `available_actions` в деталях
  `/v2/returns/rfbs/get`. Маркер первого цикла:
  `bootstrap:<slug>:rfbs_return_actions_v1`.
- Возвраты в ПВЗ приходят из возвратных отгрузок и прикладных сообщений
  `Seller_Notification*`. Завершённые/полученные записи подавляются. Маркер
  первого полного обхода: `bootstrap:<slug>:return_giveout_actions_v1`.
- `/v1/removal/from-stock/list` создаёт уведомление только для ещё доступного
  вывоза с будущим сроком утилизации. Прошедшие, отменённые и утилизированные
  записи сохраняются без отправки. Маркер первого полного обхода:
  `bootstrap:<slug>:removal_actions_v1`.
- `/v3/supply-order/list` и `/v3/supply-order/get` обрабатываются по каждой
  поставке: `COMPLETED` означает завершённую приёмку, состояние подтверждения
  отчётов/актов означает необходимость согласования. Маркер первого цикла:
  `bootstrap:<slug>:supply_actions_v1`.
- Жалобы покупателей отслеживаются по прикладным уведомлениям Ozon, так как
  отдельного read-only списка жалоб Seller API не предоставляет. Карточка
  создаётся только при наличии признака жалобы/оспаривания.

## М.Видео

Интеграция включается наличием `MVIDEO_API_KEY`. Ключ передаётся только в заголовке `api-key` на официальном адресе API Личного кабинета поставщика `https://api.sellers.mvideo.ru`; production-конфигурация отклоняет другой домен или HTTP, а значение ключа не выводится в лог. Для текущего набора уведомлений ключу нужны области `Просмотр заказов` и `FBS: Просмотр заказов`.

Если `MVIDEO_TELEGRAM_CHAT_ID` и `MVIDEO_TELEGRAM_TOPICS_JSON` пусты, маршрут копируется из первого кабинета `OZON_ACCOUNTS_JSON` только ради обратной совместимости. В production обе переменные задаются явно: отдельная форум-группа М.Видео, тема `sales` с названием «Заказы М.Видео» и тема `system` с названием «Системные уведомления». Это исключает попадание событий М.Видео в Ozon-группы.

Сервис использует `/v2/fbs/reserves/new` для новых заказов и `/v2/fbs/reserves` для сверки статусов за период. `MVIDEO_LOOKBACK_HOURS` задаёт отдельное окно сверки М.Видео и по умолчанию равно 720 часам (30 дней), чтобы изменения длительных заказов не выпадали из общего 72-часового bootstrap-окна Ozon. При первом успешном опросе маркеры `bootstrap:mvideo:fbs_new_reserves` и `bootstrap:mvideo:fbs_reserves` фиксируют текущую историю без рассылки. После этого события дедуплицируются по номеру резерва и статусу. В SQLite сохраняются только номер резерва и статус.

История читается страницами по 100 записей. Если защитный предел пагинации исчерпан на полной странице, цикл считается ошибочным и bootstrap-маркер не записывается; сервис повторит запрос, а ошибка останется в техническом логе.

Поддерживаются статусы: новый заказ, ожидание подтверждения, ожидание и начало сборки, ожидание доставки, прибытие машины на склад М.Видео, успешная или неуспешная приёмка, отмена и необходимость повторной поставки. API не возвращает в этих методах название товара, цену или дедлайн; уведомление использует доступные коды товара, количество, поставку, объект и фактическое время.

Проверка после подключения:

```bash
docker compose -f docker-compose.yml -f docker-compose.relay.yml logs --tail=200 ozon-notify \
  | grep -E 'M.Video|mvideo'
```

Успешный цикл не обязан создавать сообщение, если новых заказов или изменений нет. Подтверждением служат отсутствие API-предупреждений, заполненные bootstrap-маркеры и последующие естественные события. Не отправляйте искусственные сообщения в рабочую группу.

Ответ `400` с сообщением о ключе или `401` означает, что М.Видео не принимает выпущенный ключ: проверьте, что скопировано значение из окна после создания, ключ не отозван и у него отмечены нужные области. Для ручной проверки используйте read-only метод `GET /v2/checking-connection`. После замены `MVIDEO_API_KEY` пересоздайте контейнер. `429/5xx` повторяются автоматически; Ozon при этом продолжает работать.

## Надежность и данные

- Webhook дает быстрый сигнал, polling остается страховкой. Общий десятиминутный маркер статуса отправления подавляет только конкурентный дубль webhook/polling; последующие реальные изменения продолжают обрабатываться.
- Если Telegram временно не принял webhook-событие, endpoint отвечает `503`, событие не фиксируется обработанным и Ozon может повторить доставку.
- Регистрация webhook повторяется при временном ответе Ozon `429`; после исчерпания повторов ошибка остаётся в техническом логе.
- Дедупликация хранится в SQLite; перед переносом делайте резервную копию:

```bash
cp data/ozon_notify.sqlite3 data/ozon_notify.sqlite3.$(date +%F-%H%M).bak
```

- Если SQLite не открывается после переноса:

```bash
mkdir -p data
chown -R 10001:10001 data
docker compose -f docker-compose.yml -f docker-compose.relay.yml restart ozon-notify
```

- Ошибка одного метода Ozon или М.Видео не должна останавливать остальные источники.
- Ответы Ozon/М.Видео `4xx/429/5xx`, сетевые сбои и ошибки конфигурации остаются в техническом логе и не отправляются менеджерам.
- Секреты хранятся только в `.env` или менеджере секретов. Не копируйте их в Docker-образ, логи, tickets или документацию.

## Прикладные уведомления

Каждое уведомление должно быть понятным оператору без знания API:

- человеческий заголовок: что произошло и с каким заказом/кабинетом;
- приоритет: `Критично`, `Важно` или `Инфо`;
- срок по Москве (`МСК`), если у события есть дедлайн;
- одно явное действие: что проверить, подтвердить, упаковать, связаться или открыть;
- короткий контекст без raw API-ответов, endpoint-ов, stack trace и фрагментов кода.

Технические детали остаются в безопасных логах. Системная тема не используется для ошибок интеграции.

## Добавление кабинета

1. Создать для кабинета супергруппу, включить темы и добавить company-бота администратором с правом управления темами.
2. Создать активные разделы: продажи FBS, заказы realFBS, жалобы покупателей, возвраты и поставки FBO.
3. Добавить новый кабинет в `OZON_ACCOUNTS_JSON` с собственной авторизацией, `telegram_chat_id` и картой `telegram_topics`.
4. Оставить `BOOTSTRAP_SEND_EXISTING=false` и пересоздать контейнер. История нового кабинета будет сохранена без отправки старых событий.
5. Проверить доступность Ozon API, регистрацию webhook, `/health`, список запущенных аккаунтов в логах и отсутствие ошибок Telegram. Не использовать тестовые сообщения в рабочих группах без согласования.
